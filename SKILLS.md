# Роль и Контекст

Ты - фронтенд разработчик, специализирующийся на разработке легких интерфейсов на базе переиспользуемых компонентов.
Твоя цель - создавать компоненты с оглядкой на будущее, что ими далее могут воспользоваться при разработке другого функционала.

# Cтили

Стили хранятся в файлах .pcss рядом с index.ts, экспортирующим ui/model. .pcss импортируется в index.ts текущего слоя в самом начале.

## Правила использования БЭМ (Блок, Элемент, Модификатор)

При верстке интерфейсов обязательно использовать методологию **BEM (Block, Element, Modifier)**. Это обеспечивает независимость компонентов, повторное использование кода и легкую поддержку проекта.

### Основные понятия

*   **Блок (Block):** Независимый компонент страницы, который может повторно использоваться.
    *   Имя определяет смысл («что это?»): `.menu`, `.button`, `.card`.
    *   **Нельзя** использовать селекторы тегов (`div`, `span`) или id.
    *   Блок не должен задавать себе внешние отступы (`margin`) или геометрию, влияющую на окружение.
*   **Элемент (Element):** Составная часть блока, которая не может использоваться в отрыве от него.
    *   Имя отделяется **двумя подчеркиваниями**: `.block__element`.
    *   Примеры: `.menu__item`, `.card__title`.
    *   **Нельзя** делать вложенность имен вида `.block__elem1__elem2`. Допустим только один уровень: `.block__elem2`.
*   **Модификатор (Modifier):** Определяет внешний вид, состояние или поведение блока/элемента.
    *   Имя отделяется **двумя дефисами**.
    *   Примеры: `.button--isPrimary`, `.menu__item--isLink`.
    *   **Нельзя** использовать модификатор самостоятельно. Он всегда применяется *вместе* с классом блока или элемента: `class="button button-primary"`.
*   **Утилиты (utils):** Дополнительные классы. Чаще всего это классы состояний (.isActive, .isHover, .isDisabled, .isInvisible etc), позиционирование и геометрия (.mar-8, .pad-16, .w-auto, .w-fit, .flex-row), форматирование (.text-center, .bold, .h1, .h2, .h3, .underline, .color-light-gray, .color-dark-red). Классы состояний используются на блоке или его элементах, а остальные можно применять к контенту внутри блока (например к тому, что мы не знаем заранее или часть контента передается разметкой. В этой разметке можно использовать все утилиты). Классы состояния реализуются в каждом блоке отдельно, глобально они не объявляются.

### Пример правильной структуры (HTML)

```html
<!-- Блок -->
<div class="card card-featured"> 
  <!-- Элементы внутри блока -->
  <img class="card__image" src="..." alt="...">
  <h2 class="card__title">Заголовок</h2>
  <div class="card__buttons">
      <button class="button"> // компонент button
          <div class="button__label">Назад</div>
      </button>
      
      <button class="button button--isDark .isDisabled .isInvisible"> // компонент button
          <div class="button__label">Оставить заявку</div>
      </button>
      
      <button class="button button--isOutline">
          <div class="button__label">Подробнее</div>
          <div class="button__icon">-></div>
      </button> // компонент button
  </div>  
  
</div>
```

#### Золотые правила БЭМ

0. НИКОГДА не создавай стили, привязанные к странице. Никогда не создавай стили страниц. Все стили должны распределяться по БЭМ на блоки или выноситься в глобальные линейные (не вкладываемые) утилиты.
1. **Принцип миксинов**: Если блоку надо задать геометрию или отступы вокруг (НЕ В БЛОКЕ), используй контекст родителя и позиционируй элемент в нём. Не задавай блоку то, что меняется от контекста. Вместо `<button class="button profile__button">` пиши `<div class="button">` и в стилях parent ссылайся на .button. 
2. **Принцип расширяемости**: Все блоки должны расширяться или переопределяться в основном на основе своих модификаторов. Нельзя полностью описывать блок в его родителе. Базовые стили блока (сам блок без модификаторов) должны определять самые часто-используемые свойства.
2. **Принцип наследования**: Стили должны описываться вложенной структурой. Сначала идут переменные var, затем свойства блока, его состояния, элементы, медиа-запросы, только после - модификаторы.
3. **Семантика имен:** Классы должны описывать функцию (зачем этот элемент?) или его внешний вид. Если разные по функционалу кнопки можно объединить в класс по визуалу - нужно это делать (.button--isOutline, .button--isDark, .button--isSquare, модификаторы размеров кнопки). 
4. **Принцип избегания привязки к страницам**: избегай в именовании классов и блоков привязку к странице. Нельзя `home, home-page, home__element` и проч, что привязывается к конкретной странице.

Следуй единому шаблону для всех стилей блоков:
```pcss
.<block-name> {
    --<block-name><property>: value;
    --<block-name><property>Cur: var(--<block-name><property>);    
    --<block-name><property><state>: value;    
    
    --<block-name><element-name><property>: value;
    
    property: var(--<block-name><property>Cur);
        
    &.<state>,     
    &:<state> {
        --<block-name><property>Cur: var(--<block-name><property><state>)
    }

    &__<element-name> {
        property: var(--<block-name><element-name><property>);
    }

    @media (--any-media) {
        --<block-name><property>: any-value;
        --<block-name><property><state>: any-value;
        --<block-name><element-name><property>: any-value;
    }

    &--is<Modificator> { // begins with is, 'isPrimary', 'isDanger' etc.
        --<block-name><property>: any-value-2;
        --<block-name><property><state>: any-value-2;
        --<block-name><element-name><property>: any-value-2;
            
       @media (--any-media) {
       --<block-name><property>: any-value-3;
        --<block-name><property><state>: any-value-3;
        --<block-name><element-name><property>: any-value-3;
       }
    }

   &--is<Modificator> & {
       &__<element-name> {
           uniq-property: value; // or use variable defined in this `&--is<Modificator> {}`
       }
   }
}
```

### Components

Каждый компонент имеет обязательный набор пропсов (обычно наследуются от базового интерфейса IComponent)
```tsx
{
    extraCN: Record<string, boolean> -- классы-модификаторы
    utilCN: string[] -- утилитарные классы
    extraAttrs: Record<string, string> -- дополнительные атрибуты на блок
}
```

Стилизация в компоненте строится на базе хука useBEM(). Используй в bem(название элемента, { extraCN, utilCN }).
Абсолютно все элементы блока должны стилизоваться через функцию bem:
```jsx
<div class={bem("", { extraCN, utilCN })} {...extraAttrs}>
    <div class={bem("heading")}>title</div>
    <div class={bem("img")}>
        <Image src={"/path/to/pic.png"} alt={"description"} />
    </div>
    <div class={bem("content")}>
        some content of article
    </div>
</article>
```

Старайся избегать модификаторов на вложенные элементы блока. Лучше стилизовать элементы блока через модификатор блока.

# Правила ведения архитектуры Feature-Sliced Design (FSD)

При разработке интерфейсов обязательно следовать методологии **Feature-Sliced Design (FSD)**. Это делит кодовую базу на понятные слои, изолирует бизнес-логику и устраняет запутанные циклические зависимости.

## 1. Иерархия слоев (Layers)

Код строго разделен на **7 слоев**. Слои расположены сверху вниз по степени их специфичности.

> ⚠️ **Главное правило:** Нижележащий слой никогда не может импортировать что-либо из вышележащего слоя. Импорты идут только снизу вверх.

*   **app:** Инициализация приложения (провайдеры, глобальные стили, роутинг).
*   **pages:** Страницы приложения. Собирают функциональность из нижних слоев в готовые экраны.
*   **widgets:** Крупные самостоятельные блоки страниц (например, `Header`, `ProductGrid`).
*   **features:** Действия пользователя, несущие бизнес-ценность (например, `AddToCart`, `LikeButton`, `AuthByEmail`).
*   **entities:** Бизнес-сущности (например, `User`, `Product`, `Order`). Содержат логику данных и простые UI-компоненты.
*   **shared:** Переиспользуемый базис без привязки к бизнес-логике (UI-кит, API-клиенты, хелперы).

## 2. Анатомия слайсов и сегментов

Слои `pages`, `widgets`, `features`, `entities` делятся на **слайсы** (смысловые модули) и **сегменты** (техническое разделение).

Пример структуры сущности (`entities`):
```text
src/
└── entities/
    └── user/                   # Слайс (сущность пользователя)
        |__ api/ 
        |  |__ /<operation-name>.query.ts # получение данных с бека и их маппинг или простейшая обработка под формат.
        |  |__ /mock.tsx       # моки для msw
        |  |__ /mock.handlers.tsx # обработчики для msw
        |__ config/             
        |  |__ /types.ts       # типы (типы пропсов для всех ui этого слоя, типы для контекста, хуков, стора, моделей и тп - все типы в этом слое)
        |  |__ /const.ts       # константы
        |  |__ /ctx.ts         # контекст (обычно просто export context = createContext({}))
        |  |__ /index.ts       # Экспортирует все из слоя config.
        ├── ui/                 # Компоненты (UserCard, UserAvatar)
        ├── model/              # Бизнес-логика (store, actions, selectors, hooks)
        ├── lib/                # Внутренние хелперы слайса
        └── index.ts            # Публичное API (Public API)
        |__ user.pcss           # стили, импортируются в index.ts.
```

shared обязательно делим на слои
```text
src/shared/
|__ lib/ -- библиотеки и функции, которые можно переиспользовать практически в любом контексте
|__ ui/ -- базовый тулкит (layout, button, tabs, card, checker, input, textarea, flex, grid, slider, select, popup, popover и тп как в Mui).
|__ types/ -- общие типы
|__ const/ -- общие константы
```

## 3. Золотые правила FSD

1.  **Strict Public API:** Каждый слайс обязан иметь файл `index.ts`, который является его «витриной». Извне слайса разрешено импортировать файлы **только** через этот индексный файл.
    *   ❌ *Плохо:* `import { UserCard } from '@/entities/user/ui/UserCard'`
    *   ✅ *Хорошо:* `import { UserCard } from '@/entities/user'`
2.  **Запрет кросс-импортов на одном слое:** Слайсы на одном и том же слое не знают друг о друге.
    *   ❌ *Запрещено:* Импортировать что-то из `features/auth` внутрь `features/payment`.
    *   💡 *Решение:* Перенесите общую логику на слой ниже (`entities`) или объедините их на слое выше (`widgets`).
3.  **Изоляция Shared:** Слой `shared` должен быть полностью «глупым» с точки зрения бизнеса. Никаких упоминаний `user`, `product` или токенов авторизации в `shared/ui` быть не должно.

## Пример правильного импорта в компоненте

```typescript
// Компонент находится в widgets/product-card

// ✅ МОЖНО: Импорты снизу вверх (из features, entities, shared)
import { AddToCartButton } from '@/features/add-to-cart'; 
import { ProductPrice } from '@/entities/product';
import { Button } from '@/shared/ui/button';

// ❌ ЗАПРЕЩЕНО: Импорт с вышележащего слоя или со своего уровня
// import { CartWidget } from '@/widgets/cart'; — Кросс-импорт (один слой)!
// import { OrderPage } from '@/pages/order'; — Импорт сверху вниз!
```
